# تكليف تنفيذي موحد لـ Codex — SKY LINE Access Control Management Center

**نفّذ هذا التكليف داخل المشروع القائم `C:\awwal-akher` على Windows؛ لا تنشئ مشروعًا جديدًا، ولا تكتفِ بكتابة خطة.** أنت المسؤول عن التصميم والتكويد والاختبارات والتوثيق. ابدأ بمراجعة حالة الملفات والتعديلات التي نفذتها الجلسة السابقة، ثم أكمل من الحالة الحالية بأقل تغييرات تكسّر السلوك الموجود. لا تطلب مني موافقة بعد كل ملف؛ اطلبها فقط قبل أوامر حساسة تؤثر على أجهزة حقيقية، فتح باب فعلي، حذف بيانات، تعديل صلاحيات مستخدم حقيقي، ترحيل إنتاجي، أو إيقاف خدمة حية.

## 1. السياق المؤكد وحالة المشروع

- المشروع: SKY LINE / أول وآخر — React + TypeScript + TanStack Start + Vite، موجود في `C:\awwal-akher`، ويُعرض عبر `http://100.69.92.116:8080/` باستخدام Tailscale.
- الجهاز: Hikvision DS-K1A340WX، firmware V1.2.7، عنوان LAN `192.168.1.21`، HTTP port `80`، اسم المستخدم `admin`، HTTP Digest.
- تم التحقق عمليًا من `GET /ISAPI/System/deviceInfo`، وعدد المستخدمين `2`، والبحث عن المستخدمين: `1 / mk` و`2 / yousef`، ومن استعلام سجلات الأحداث `totalMatches=57`. واجهة البرنامج نجحت لاحقًا في سحب الموظفين وعرض 24 حدث تحقق في الفترة القديمة، مع فصل أحداث النظام؛ الـ24 ليست 24 يوم حضور.
- أول تسجيلات الجهاز مؤرخة `2015` بتوقيت `+08:00` حين كانت ساعته خاطئة. جرى ضبط ساعة الجهاز على `2026-10-22` بتوقيت القاهرة `+03:00` يدويًا. لا تعدّل timestamps التاريخية ولا تنسبها إلى 2026. مسار `/ISAPI/System/time/dst` أعاد `notSupport`. الجهاز أظهر دعم NTP أو manual، دون إثبات إعداد NTP فعليًا.
- جرى إصلاح خطأ `node:undici` وServer Functions في العمل السابق وفق تقرير Codex، مع اختبارات بناء ناجحة، لكن تأكد من حالة الملفات الحالية ولا تثق في تقرير قديم وحده. خمس اختبارات عامة قديمة متعلقة بـOG/PWA كانت فاشلة حسب التقرير؛ فرّقها عن أي regression جديد.
- توجد بالفعل ملفات: `src/lib/hikvision.server.ts`، `src/lib/hikvision.functions.ts`، `src/lib/hikvision-parse.ts`، `src/lib/hik-connect.server.ts`، `src/lib/attendance.ts`، `src/components/attendance-board.tsx`، `src/components/device-desk.tsx`، وغيرها. استخدم وحداتها واستدعاءاتها بدل نسخ تكامل جديد.
- المستخدم يعمل عن بعد من Android Termux عبر SSH/Tailscale؛ لا تعتمد على إمكانه الوصول الفعلي إلى الكمبيوتر أو شاشة البصمة الآن.

## 2. قراءة المراجع وبناء مصفوفة القدرات — إلزامي قبل أي كتابة للجهاز

اقرأ الملفات الموجودة بمجلد `REFERENCES` ضمن حزمة المهمة إن نُقلت إلى الكمبيوتر، وأي كتيبات SDK إضافية في المشروع. المراجع الواردة بالحزمة:
- `Push_SDK_Access_Control_Protocol_20230927.pdf` (308 صفحات): مواصفات Access Control تشمل الأشخاص والكروت والوجوه والبصمات والصلاحيات والجداول والأبواب والأحداث وواجهات ISAPI.
- `PUSHSDK_Access_Specifications_20260303.pdf`: OTAP HTTPS Push SDK والاتصال والتسجيل ودفع الأحداث؛ هذا نمط اتصال مختلف ولا يجوز اعتباره مماثلًا لاتصال ISAPI المحلي.
- `PUSH_SDK_DEMO.pdf`: أمثلة توضيحية.
- `Hik_Connect_Teams_OpenAPI_Developer_Guide_20260904.pdf`: APIs السحابة لإدارة الأشخاص والصلاحيات والأحداث، تختلف في العناوين والمصادقة عن ISAPI المحلي. لا تفترض توفر اعتمادات OpenAPI.
- `Hik_Connect_Teams_Network_SDK_Android_Developer_Guide.pdf`: SDK تطبيقات Android، ليس بديلًا تلقائيًا عن واجهات السيرفر الحالي.

افحص بشكل **read-only أولًا**:
- `GET /ISAPI/AccessControl/capabilities`
- `GET /ISAPI/AccessControl/UserInfo/capabilities?format=json`
- إمكانيات الكروت، البصمات، الوجوه، القارئ، الأبواب، جداول الصلاحيات، أرقام الأبواب الحقيقية، المداخل/المخارج والأحداث باستخدام مسارات capabilities الموثقة.
- واجهات device info وtime التي سبق إثباتها.

أنشئ Capability Matrix لكل جهاز ولكل وظيفة: `supported / unsupported / unverified` + endpoint + مستند/قسم مرجعي + نتيجة probe + القيود. **لا تظهر وظيفة مفعلة لمجرد أنها واردة بالدليل؛ لا بد أن يدعمها DS-K1A340WX بإصداره الحالي**. ميّز كذلك بين صلاحيات الجهاز الفعلية والميزات المنطقية داخل البرنامج.

## 3. المطلوب: واجهة عربية متكاملة وبسيطة للغاية

حوّل واجهة SKY LINE إلى لوحة تشغيل مفهومة للمستخدم غير التقني، RTL بالكامل، مناسبة للموبايل والكمبيوتر، مع قائمة تنقل واضحة وأزرار أفعال حقيقية وليست شكلية. أضف «مركز التحكم بالبصمة والأبواب» بأقسام مترابطة:

**لوحة التحكم الرئيسية**: حالة الاتصال، اسم الجهاز والموديل وإصداره، آخر مزامنة، عدد الموظفين، عدد الأبواب الفعلية، أحداث اليوم، حالات الاستثناء، أخطاء المزامنة، سلامة الساعة والتوقيت، ومؤشر capabilities.

**المستخدمون/الموظفون**: زر واضح «+ إضافة مستخدم»، البحث، التصفية، عرض التفاصيل، إضافة/تعديل/تعطيل/حذف (الأخير بتأكيد صريح وفحص آثار الحذف)، رقم موظف فريد، اسم، حالة التفعيل، صلاحيات الوصول، فترة الصلاحية، ربط الشخص بجهاز أو أكثر، استيراد/تصدير CSV/XLSX مع Preview قبل الكتابة، ومنع التكرار. عمليات الكتابة تستخدم واجهات الموثقة *إذا أثبتت capability* مثل `POST /ISAPI/AccessControl/UserInfo/Record?format=json` أو `PUT /ISAPI/AccessControl/UserInfo/SetUp?format=json` و`PUT /ISAPI/AccessControl/UserInfo/Modify?format=json`، لا تخمّن الـpayload.

**وسائل التحقق**: كروت الدخول، صورة الوجه وربطها بالشخص، بصمة الإصبع، رقم PIN وطرق التحقق المتاحة. أزرار «إضافة كارت»، «إضافة صورة وجه»، «تحديث»، «إلغاء» و«بدء جمع البصمة» فقط عند دعم الجهاز وإمكانية التنفيذ الحقيقية. راعِ حجم ونوع صور الوجه ومتطلبات المكتبة وFDID/FPID وفق الدليل والجهاز. لا تدّعِ إمكانية التقاط البصمة أو استخراج قوالب بيومترية إذا لم يؤكد الجهاز هذا الدعم. تجنب إظهار أو تسجيل بيانات بيومترية سرية بلا داعٍ.

**الأبواب ونقاط الدخول**: زر «+ إضافة باب» ينشئ تعريفًا **منطقيًا** داخل البرنامج لربط باب/قناة *موجودة ومؤكدة في عتاد الجهاز* باسم وموقع وملاحظات؛ لا تنشئ قناة باب في الجهاز إذا لم توجد فعليًا. اعرض doors/channels الحقيقية من capabilities، وحالة الاتصال/الباب إن أمكن، وتعديل التسمية والربط. أضف التحكم اليدوي «فتح لحظي / إغلاق / إبقاء مفتوحًا» فقط إذا تدعمه الواجهة وحسب صلاحيات المستخدم، مع تأكيد خاص وتحذير لعمليات always-open/always-close، وسجل تدقيق كامل؛ لا تنفذ فتحًا فعليًا أثناء الاختبار دون موافقة. مرجع باب محتمل في الدليل `PUT /ISAPI/AccessControl/RemoteControl/door/<doorID>` بعد تحقق endpoint وdoorID والطراز.

**الصلاحيات والجداول**: منح موظف صلاحية باب أو مجموعة أبواب، خطط أسبوعية، أوقات السماح، عُطلات رسمية ومجموعات عطلات، قوالب permission/verify schedules، وربطها بالشخص. عمليات عرض/تعديل مقيدة بقدرات الجهاز. حافظ على قابلية رؤية «لماذا هذا الموظف ممنوع من الدخول» من خلال التشخيص المرتبط بالخطة.

**الحضور والانصراف**: استيراد سجلات التحقق الفعلية مع pagination وتصفية أحداث النظام، مقارنة first/last punch بقواعد عمل معلنة، دوام الليلي/عبور منتصف الليل، السماحيات، العطلات والإجازات، التأخير والانصراف المبكر والغياب والانصراف المفقود، ورديات متعددة، تقرير يومي/أسبوعي/شهري، Excel/PDF عند توفر بنية المشروع، وفصل «حدث تحقق» عن «حضور» وعن «فتح باب». لا تعتبر أحداث 2015 حضورًا في 2026، ولا تحسب مدة 19 ساعة كدوام طبيعي دون قواعد استثناء وتحذير. احتفظ بـraw event (معلومات الجهاز، timestamp الأصلي، offset، serialNo، major/minor، employeeNo، source) ثم normalized event بعد التحقق. زود المستخدم بشاشة مراجعة ومعالجة الاستثناءات.

**سجلات الأحداث والتشخيص**: أحداث الدخول الناجح/الفاشل/الإنذارات/النظام، الفلاتر، البحث، الصور المرتبطة بالأحداث إذا كانت مدعومة وآمنة، تصدير، عداد raw/valid/deduplicated، معلومات source وحالة الاستيراد.

**الأجهزة والاتصال**: إضافة جهاز إلى البرنامج، اختبار الاتصال، مسح خصائص الجهاز، معلومات إصداره وسعته، مقارنة الساعة، فحص وإصلاح انقطاع الاتصال، إعدادات Polling/Sync والـNTP إن كانت مدعومة، دون تعديل إعدادات الجهاز ضمن مجرد فتح شاشة الإعدادات. الحفاظ على Cloud Hik-Connect بجانب الاتصال المحلي دون خلط مصادقتهما.

**الإعدادات والأمان**: أدوار وصلاحيات Admin/Operator/Viewer؛ فقط مسؤول مخوّل يمكنه حذف مستخدم أو التحكم في الباب أو تغيير صلاحياته؛ تأكيد ثنائي الخطوة للعمليات الحساسة، سجل audit من/متى/ماذا/النتيجة، أخطاء مفهومة وغير كاشفة للأسرار.

## 4. اشتراطات UX وجودة التصميم

- اعمل UI عربية RTL حقيقية، بأسلوب بصري نظيف ومباشر، مع قائمة جانبية/سفلية للموبايل، أزرار واضحة «إضافة مستخدم» و«إضافة باب» و«سحب الآن»، نوافذ/نماذج سهلة، تحميل/نجاح/فشل/تأكيد وإلغاء، مؤشر تقدم أثناء المزامنة.
- لا تمرير أفقي للصفحة عند 320 و360 و375 و390 و768 و1280 بكسل؛ الجداول الواسعة داخل حاوية جدول فقط، وليس كل الصفحة. اختبر العربية والأرقام والتواريخ وأزرار اللمس والنماذج على Android.
- أبقِ تجربة الاستيراد اليدوي والبوابة السحابية الحالية، ولا تُفسد الحسابات أو UX الموجودة. تجنب أزرار وهمية؛ لكل زر وظيفة حقيقية وحالة unavailable مفسَّرة.

## 5. Architecture، النقل والأمان

- جميع طلبات الجهاز والمصادقة HTTP Digest تتم في SERVER فقط، لا تسمح للمتصفح بالاتصال المباشر بـLAN ولا تسرّب باسورد الجهاز في code أو localStorage أو logs.
- استخدم store آمن على الخادم بأقل صلاحيات، لا تكتب أسرار في ملفات عامة أو Git. افحص الحماية من SSRF وDNS rebinding مع allowlist للأجهزة المضافة ومراجعة صحة الـIP والـports والـredirects. لا تضع `rejectUnauthorized:false` عامًا؛ استخدم استثناءات مقيّدة ومصرّح بها فقط للأجهزة المحلية ذات الشهادات الذاتية عند اللزوم.
- افصل local ISAPI عن Hik-Connect OpenAPI وعن Push SDK transport. لا تفعّل Push webhook أو تغيّر منصة الجهاز إلا بعد تحقق إمكانيته وموافقة المستخدم.
- راجع مكوّنات authentication/authorization الحالية قبل تعريض Server Functions لعمليات كتابة أو تحكم بالأبواب. اتبع principle of least privilege، احمِ من CSRF حيث ينطبق، تحقق من كل البيانات على السيرفر، limit/timeout/retry مع backoff.
- خزّن بيانات الأشخاص والصلاحيات والأحداث في مخطط واضح مع uniqueness keyed per-device، migration آمنة، upsert idempotent، سجل العمليات والأخطاء، استراتيجية rollback/backup. لا تعدّل قاعدة البيانات الإنتاجية دون فهم مخططها ونسخها أولًا.
- المزامنة التلقائية *حقيقية على السيرفر* وليست Checkbox وهمية في localStorage؛ جلب incremental يميز الانقطاع وإعادة المحاولة والصفحات وعمر الأحداث، ويوقف المهام المتكررة بشكل نظيف، ولا يرسل أوامر كتابة إلى الجهاز تلقائيًا.

## 6. خطوات التنفيذ والاختبارات — نفّذ لا تكتفِ بالخطة

1. افحص repo وgit status وسجل التعديلات السابقة وأحدث تقرير `docs/hikvision-20261022-report.md` والنسخ الاحتياطية؛ لا تعكس الشغل الناجح. جهّز backup منفصل للتعديلات الجديدة.
2. اجمع Capability Matrix من الدليل والـGET الفعلي واقترح ترتيب تنفيذ داخلي، ثم نفّذ كل ما تأكد دعمه. ضع Unsupported features في الواجهة بشكل معطّل مع سبب محدد؛ لا تلفّق سلوكًا.
3. نفّذ واجهة موحّدة وخدمات server adapters، والـCRUD المستند إلى قدرات الجهاز، مع mocks آمنة للاختبارات، وعناصر التحكم عالية الخطورة قابلة للتنفيذ فقط بعد موافقات تفاعلية من المستخدم.
4. اختبر `typecheck` وunit/integration/E2E والبناء بدون ترحيلات DB مفاجئة. استخدم Playwright لاختبار الشاشات الضيقة والواسعة؛ اختبر real device *read-only* إذا أمكن الحصول على بيانات الدخول في جلسة خاصة دون كشفها؛ أي اختبار كتابة على الجهاز يكون باختيار المستخدم وببيانات تجريبية غير مؤثرة وبخطة تراجع.
5. لا توقف SSH/Tailscale ولا تغيّر route ولا توقف سيرفر `8080` الحي بلا ضرورة وموافقة. إن احتجت staging، شغّله على منفذ منفصل وتحقق قبل الاستبدال.
6. اعمل تقريرًا نهائيًا بالعربية يتضمن: ما نُفّذ فعليًا، ما لم يدعمه هذا الموديل، كل endpoint من الجهاز وحالة التحقق، الملفات المتغيرة، نتائج الاختبارات (الحقيقي والمحاكى منفصلان)، عناصر الأمان، أماكن النسخ الاحتياطية، طريقة التشغيل، وما يتطلب موافقة/تجهيزات مادية إضافية.

**تعريف النجاح**: أفتح SKY LINE على موبايل Android، أرى لوحة إدارة مبسطة بها «إضافة مستخدم» و«إضافة باب» مع فهم الفرق بين الباب الافتراضي والباب الفعلي، أستطيع إدارة بيانات الموظفين وصلاحياتهم وأحداثهم وإجراء التحكم المدعوم فقط من جهاز DS-K1A340WX؛ مع اختبار فعلي موثّق وعدم الإضرار ببيانات الجهاز أو توفر الخدمة. إن تعذر جزء بسبب عدم دعم الجهاز أو غياب سر أو عتاد فاعرضه بوضوح ولا تدّعِ اكتماله.
